# Волна 1: объяснения к ADR 0007–0014 и вопросы с собеседования

Для каждого ADR: что решили, новые понятия одной фразой, аналогия из жизни, что может
сломаться, три вопроса с собеседования (ответ по-русски + ключевая фраза по-английски).

---

## ADR-0007. API-контракт

### Что решили

Фронтенд и бэкенд договариваются через **контракт** — файл `openapi.json`, где перечислены
все адреса, поля и ошибки. Этот файл мы не пишем руками. Он **генерируется из кода
бэкенда** (классы DTO в NestJS), **хранится в репозитории** и виден в каждом pull request
как обычный diff. Из него генерируются Angular-клиент и моки для тестов.

Проверка `api:check` в CI заново строит контракт из кода и сравнивает с файлом в
репозитории. Забыли перегенерировать — CI красный. Это тот же приём, что `tokens:check`.

### Новые понятия

- **REST** — стиль API, где у каждой сущности свой адрес (`/envelopes/17`), а действие
  задаётся методом HTTP (GET — прочитать, POST — создать).
- **OpenAPI** — стандартный формат описания REST API, понятный и людям, и программам.
- **DTO** (data transfer object) — класс, описывающий форму запроса или ответа.
- **Code-first** — сначала код, контракт получается из него. **Contract-first** — наоборот.
- **Генератор клиента** — программа, которая по контракту пишет TypeScript-сервисы.
- **`httpResource`** — способ Angular загрузить данные и получить их сразу как сигнал
  (значение, которое само сообщает об изменении) вместе с состоянием «загружается / ошибка».
- **Мок** — подделка сервера для тестов. **MSW** перехватывает сетевые запросы и отвечает
  заготовленными данными.

### Аналогия

Чертёж детали. Инженер (бэкенд) делает деталь и по ней автоматически печатается чертёж.
Чертёж лежит в общей папке, и любое изменение в нём видно всем. Сборщик (фронтенд) работает
только по чертежу. Контролёр (CI) каждый раз сверяет: чертёж в папке соответствует детали?

### Что я изменил относительно ваших ожиданий — прямо

- Источник правды — **код, а не openapi.yaml**. Причина: при contract-first серверу нужен
  второй механизм проверки запросов (вместо class-validator), и CLAUDE.md пришлось бы
  менять. Code-first оставляет одну точку правки и стандартный NestJS.
- `libs/shared/api-types` с типами, написанными руками, **убираем**: общие типы теперь
  генерируются. Одну строку в CLAUDE.md надо заменить (текст есть в ADR).
- Генератор — **Orval**: он умеет и сервисы на HttpClient, и `httpResource`, и моки MSW.

### Что может сломаться

- Неаккуратные декораторы → неточный контракт (например, не указано, что поле может быть
  пустым). Лечится ревью diff-а `openapi.json`.
- Берём Nest 12 (нужен для `@nestjs/swagger` 12 и OpenAPI 3.1). Это свежая версия на
  ES-модулях; совместимость с Prisma и class-validator проверяется в первой задаче.
- Кто-то импортирует серверную библиотеку во фронтенд. Не получится: у библиотек есть
  теги, и правило Nx превращает такой импорт в ошибку lint.
- Сгенерированный клиент не лежит в репозитории: после `git pull` его надо построить
  (Nx делает это сам перед сборкой и тестами).
- Обновление Orval может поменять вид сгенерированного кода. Версию закрепляем.

### Вопросы с собеседования

1. **Почему REST, а не GraphQL?**
   GraphQL решает задачу «много разных клиентов хотят разные наборы полей». У нас один
   клиент на API, зато есть загрузка файлов, коды состояния и кеширование HTTP — в REST
   это из коробки.
   EN: _"GraphQL solves over- and under-fetching across many clients; we have one client
   per API, so REST with OpenAPI is the simpler fit."_

2. **Code-first или contract-first — и почему?**
   Code-first: один класс DTO задаёт и проверку, и тип, и схему. Сгенерированный контракт
   закоммичен и проверяется в CI, поэтому преимущество contract-first — видимый,
   ревьюируемый контракт — у нас тоже есть.
   EN: _"Code-first, but the generated spec is committed and drift fails CI — single source
   of truth with a reviewable contract."_

3. **Как вы гарантируете, что фронтенд и бэкенд не разойдутся?**
   Клиент не пишется руками, а генерируется из контракта; контракт генерируется из кода;
   CI падает, если файл контракта устарел. Изменение поля на сервере ломает компиляцию
   фронтенда, а не продакшен.
   EN: _"The client is generated from the spec, the spec from the code, and CI fails on
   drift — a breaking change becomes a compile error."_

## ADR-0008. Конвенции API и деньги

### Что решили

Единые правила для всех эндпоинтов:

- **Ошибки** — в формате RFC 9457 со стабильным **кодом** (`envelope.pdf_encrypted`).
  Сервер не присылает текст для пользователя. Фронтенд по коду берёт перевод. Список кодов
  один, и CI проверяет, что у каждого есть перевод.
- **Списки** — `page`, `pageSize`, `sort=-updatedAt`, фильтры обычными параметрами.
  В ответе `items` и `totalItems`.
- **Даты** — момент времени в UTC (`…Z`), календарная дата как `2026-11-20`.
- **Идентификаторы** — UUIDv7.
- **Версия** — в адресе: `/api/v1`.
- **Одновременная правка** — у записи есть номер версии. Прислал устаревший — получил
  409, ничего не перезаписано.
- **Деньги** — сумма целым числом в минимальных единицах плюс код валюты:
  `{ "amountMinor": 1586, "currency": "EUR" }`. Цена за единицу, количество и ставка —
  точной строкой: `"1.789"`.

### Новые понятия

- **RFC 9457 (Problem Details)** — интернет-стандарт на вид ответа с ошибкой.
- **Минимальная единица** — цент, тыйын, копейка.
- **ISO 4217** — стандарт трёхбуквенных кодов валют (EUR, KGS, RUB).
- **Число с плавающей точкой (float)** — способ хранить дроби в двоичном виде; 0,1 в нём
  точно не представимо, поэтому `0.1 + 0.2` даёт `0.30000000000000004`.
- **UUIDv7** — случайный идентификатор, первые биты которого — время создания; такие id
  идут по порядку и хорошо ложатся в индекс базы.
- **Оптимистичная блокировка** — никого не блокируем заранее, а при сохранении проверяем,
  не изменил ли запись кто-то другой.
- **Брендированный тип** — тип TypeScript «строка, но с меткой»: компилятор не даст
  передать обычную строку туда, где ждут десятичное число.

### Аналогия

Касса считает в копейках, а не в рублях с дробью: 15 рублей 86 копеек — это 1586 копеек,
и при сложении ничего не теряется. Коды ошибок — как коды на приборной панели автомобиля:
машина показывает код, а инструкция на вашем языке объясняет, что он значит.

### Что может сломаться

- Новый код ошибки без перевода — поймает CI.
- Смешение валют в одной сумме — функция сложения бросит исключение; аналитика считает по
  валютам раздельно.
- Сколько знаков после запятой у валюты (у евро 2, у иены 0), записано в **нашей
  закреплённой таблице**, а не берётся из `Intl`. Данные `Intl` зависят от версии
  браузера или Node, и одно и то же число `1586` могло бы прочитаться по-разному.
  Неизвестная валюта отклоняется. `Intl` используется только для красивого показа.
- Сумма больше 2⁵³ − 1 минимальных единиц не помещается точно в число JavaScript. Это
  около 90 триллионов евро; сервер такие значения отклоняет.
- Постраничная выдача «по номеру страницы» медленная на сотнях тысяч строк. У нас их нет;
  условие пересмотра записано в ADR.

### Вопросы с собеседования

1. **Почему нельзя хранить деньги во float?**
   Двоичная дробь не может точно представить 0,1; ошибки накапливаются при сложении и
   сравнении. Храним целые минимальные единицы, а делим на 100 только при показе.
   EN: _"Binary floating point can't represent decimal fractions exactly; we store integer
   minor units and format only at the edge."_

2. **Как фронтенд показывает ошибку на трёх языках?**
   Сервер присылает стабильный код и параметры, фронтенд берёт перевод по ключу
   `errors.<code>`. Список кодов попадает в контракт, CI проверяет наличие переводов.
   EN: _"The server returns a stable error code per RFC 9457; the client owns the
   translations, and CI checks every code has one."_

3. **Offset- или cursor-пагинация?**
   Offset: в макетах есть номера страниц и «1–7 из 12», объёмы малы. Cursor нужен для
   огромных или быстро меняющихся лент; условие перехода записано.
   EN: _"Offset pagination matches page numbers in the UI at our scale; cursor pagination
   is the documented next step for large, live lists."_

## ADR-0009. Окружения и настройки

### Что решили

Собираем приложение **один раз**. Один и тот же образ работает и в демо, и в рабочей
версии. Различия — в настройках, которые читаются при запуске:

- бэкенд читает переменные окружения, проверяет их и **отказывается стартовать**, если
  чего-то не хватает или сочетание опасное;
- фронтенд перед стартом спрашивает у сервера публичные настройки (`/api/v1/config`);
- вместо одного переключателя «демо» — отдельные именованные настройки: кто может
  регистрироваться, куда уходят письма, лимит загрузки, срок жизни аккаунта.

Адреса: `sign.`, `beleg.`, `sign-demo.`, `beleg-demo.` — **по одному поддомену демо на
приложение**. Это ответ на ваш вопрос 4.

### Новые понятия

- **Окружение** — место, где работает программа: локально, CI, демо, рабочее.
- **Переменная окружения** — настройка, которую программа получает снаружи при запуске.
- **Origin** — связка «протокол + хост + порт». Браузер разделяет по ней cookie,
  локальное хранилище и service worker.
- **Fail fast** — «падай сразу»: лучше не запуститься, чем работать с неверной настройкой.

### Аналогия

Одна и та же стиральная машина в двух квартирах: модель одинаковая, а программу стирки
выбирают ручкой. Мы не выпускаем отдельную модель «для демо».

### Почему не один `demo.`

Если оба приложения живут на одном хосте, у них общие cookie и общее локальное хранилище.
Для Belegscan это особенно важно: офлайн-чеки лежат в IndexedDB, и демо-данные не должны
попасть в ту же базу браузера, что настоящие.

### Что может сломаться

- Демо-код (песочница, перехват писем) лежит и в рабочем образе, просто выключен.
  Защита — проверка сочетаний при старте.
- Если сервер настроек недоступен, фронтенд не стартует. Показываем понятный экран ошибки.
- Новую переменную забыли добавить в `.env.example` — поймает проверка в CI.

### Вопросы с собеседования

1. **Что значит «build once, deploy many»?**
   Артефакт, прошедший тесты, без пересборки идёт во все окружения; меняются только
   настройки. Иначе в продакшене работает не то, что тестировали.
   EN: _"The artifact that passed CI is promoted unchanged; only configuration differs."_

2. **Почему не `environment.prod.ts` в Angular?**
   Замена файлов происходит при сборке — значит, на каждое окружение свой бандл. Мы
   загружаем настройки при старте приложения.
   EN: _"File replacements bake config into the bundle; we load runtime config before
   bootstrap so one bundle serves every environment."_

3. **Как вы защищаетесь от неправильной конфигурации?**
   Схема настроек проверяется при старте; опасные сочетания (песочница + реальная почта)
   запрещены; `.env.example` сверяется со схемой в CI.
   EN: _"Config is schema-validated at startup and the process fails fast on invalid or
   dangerous combinations."_

## ADR-0010. Аутентификация

### Что решили

- **Сессия на сервере.** После входа сервер создаёт случайный идентификатор сессии и
  кладёт его в cookie с флагом `HttpOnly` — JavaScript её не видит. В базе хранится
  только хеш идентификатора.
- **Пароли** хешируются Argon2id.
- **Регистрация только по приглашению.** Ссылка из письма при открытии ничего не меняет;
  приглашение «тратится» только когда человек задал пароль.
- **Восстановление пароля** — по ссылке на 1 час; после смены все сессии закрываются.
- **2FA в v1 нет**, но место для неё в процессе входа оставлено.
- SignFlow и Belegscan — **раздельные базы пользователей**, общий только код.

### Новые понятия

- **Аутентификация** — проверка, кто вы. (Авторизация — что вам можно; это ADR-0011.)
- **Сессия** — запись на сервере «этот браузер — это пользователь N до такого-то времени».
- **Cookie `HttpOnly`** — cookie, которую браузер отправляет серверу, но не показывает
  скриптам страницы.
- **`SameSite`** — правило, отправлять ли cookie при переходе с чужого сайта.
- **XSS** — атака, при которой на вашей странице выполняется чужой скрипт.
- **CSRF** — атака, при которой чужой сайт заставляет ваш браузер отправить запрос от
  вашего имени.
- **JWT** — подписанный токен с данными о пользователе, который можно проверить без базы.
- **Хеш пароля** — необратимое преобразование; по хешу пароль не восстановить.
- **Argon2id** — алгоритм хеширования паролей, специально медленный и требующий памяти,
  чтобы перебор был дорогим.
- **Соль** — случайная добавка к паролю, чтобы одинаковые пароли давали разные хеши.
- **2FA / TOTP** — второй фактор; шестизначный код из приложения, меняется раз в 30 секунд.
- **OIDC + PKCE** — стандарт входа через внешний сервис (Keycloak) и его защита для
  браузерных приложений.

### Аналогия

Гардероб. Вы сдали пальто (вошли), вам дали номерок (cookie). На номерке нет вашего имени —
только номер. Гардеробщик (сервер) по своей книге знает, чьё пальто. Потеряли номерок —
гардеробщик вычёркивает запись, и номерок больше не работает. JWT — это как записка «это
пальто Иванова», которой верят без книги: удобно, но отозвать её нельзя.

### Что может сломаться

- Нет 2FA: украденный пароль даёт доступ. Смягчение — приглашения, ограничение попыток,
  мгновенное закрытие сессий. 2FA для администраторов — первый кандидат на v2.
- Ограничение попыток само может стать оружием: если блокировать аккаунт после пяти
  ошибок, любой заблокирует чужой аккаунт. Поэтому считаем ошибки по паре «аккаунт + IP»
  и отдельно по IP. Аккаунт целиком блокируется только при переборе со многих адресов, и
  владелец сразу получает письмо со ссылкой на сброс пароля.
- Модуль `argon2` — нативный, при установке ему нужно разрешение в `pnpm-workspace.yaml`.
- Ошибка в проверке `Origin` открывает CSRF. Покрываем тестами: запрос с чужого origin
  должен получить отказ.
- Письма с приглашением могут попасть в спам (доставляемость — отдельный ADR волны 2).

### Вопросы с собеседования

1. **Cookie-сессия или JWT для SPA?**
   Для SPA на том же origin, что и API, — сессия в `HttpOnly` cookie: её не украсть через
   XSS и можно отозвать мгновенно. JWT хорош для сторонних API и мобильных клиентов.
   EN: _"For a same-origin SPA, an httpOnly session cookie: not readable by scripts and
   revocable instantly; JWTs add refresh logic without benefit here."_

2. **Как защищаетесь от CSRF, раз используете cookie?**
   `SameSite=Lax` плюс проверка заголовков `Origin` / `Sec-Fetch-Site` на всех изменяющих
   запросах; API принимает только JSON и multipart.
   EN: _"SameSite cookies plus server-side Origin and Fetch-Metadata checks on every
   state-changing request."_

3. **Как потом перейти на Keycloak, не переписывая фронтенд?**
   Приложение зависит только от cookie сессии и объекта «текущий пользователь». Сервер
   станет OIDC-клиентом и по-прежнему будет выдавать ту же cookie (схема BFF).
   EN: _"Backend-for-frontend: the API becomes the OIDC client with PKCE and keeps issuing
   the same session cookie, so the SPA doesn't change."_

## ADR-0011. Авторизация

### Что решили

- **Запрещено всё, что не разрешено явно.** Эндпоинт без объявленного правила не
  отвечает, а тест в CI находит такие эндпоинты.
- Правила — **простые функции** вида «может ли этот человек прочитать этот документ».
  Их проверяют табличные тесты.
- **Запросы к базе сразу ограничены** владельцем или группой. Не «достать всё и
  отфильтровать», а «достать только моё».
- Чужой документ отвечает **404**, а не 403: не подтверждаем даже его существование.
- SignFlow: администратор управляет пользователями, но **не видит чужие документы**.
- Belegscan: таблица «пользователь — группа — роль», группа указана в адресе запроса.
  Создатель группы — её **владелец**: только он приглашает и удаляет участников и
  назначает бухгалтера. Приглашение в группу может создать новый аккаунт. В корзину
  участник отправляет только свои неподтверждённые чеки, бухгалтер — любые.

### Новые понятия

- **Авторизация** — проверка, что вам можно.
- **IDOR** — уязвимость «поменял номер в адресе и увидел чужое».
- **Guard** — в NestJS функция, которая решает, пропустить ли запрос к обработчику.
- **Deny by default** — «по умолчанию нельзя».
- **Принципал** — тот, от чьего имени идёт запрос: пользователь с аккаунтом или внешний
  подписант по ссылке.

### Аналогия

Офисное здание. Пропуск на входе — это аутентификация. Но пропуск не открывает все
кабинеты: у каждой двери свой замок, и он проверяет, ваш ли это кабинет. Завхоз
(администратор) выдаёт пропуска, но ключей от чужих сейфов у него нет.

### Что может сломаться

- Кто-то напишет запрос к базе в обход «ограниченного» репозитория. Защита — ревью и тест
  матрицы доступа на каждый эндпоинт.
- Администратор **сервера** (не приложения) технически видит всё. Это честно записано.

### Вопросы с собеседования

1. **Чем аутентификация отличается от авторизации?**
   Первая отвечает «кто ты», вторая — «что тебе можно». Частая дыра — проверили роль, но
   не проверили, что документ принадлежит этому пользователю.
   EN: _"Authentication is identity, authorization is permission — and most real bugs are
   missing ownership checks, not missing role checks."_

2. **Почему 404, а не 403?**
   403 подтверждает, что ресурс существует. Для чужих документов это утечка информации.
   EN: _"A 403 confirms the resource exists; returning 404 avoids leaking that."_

3. **Как убедиться, что новый эндпоинт не остался без проверки?**
   Глобальный guard отклоняет маршрут без объявленной политики, а тест перебирает все
   маршруты и падает, если политика не объявлена.
   EN: _"A global deny-by-default guard plus a test that enumerates every route and fails
   if one has no declared policy."_

## ADR-0012. Файлы: хранение, шифрование, проверка загрузок

### Что решили

- Файлы лежат на диске сервера, но код работает с ними через интерфейс `FileStore`,
  чтобы потом без переделки перейти на объектное хранилище.
- **Конвертное шифрование.** Каждый файл шифруется своим случайным ключом. Этот ключ
  шифруется **мастер-ключом** и лежит в базе рядом с записью о файле. Мастер-ключ — в
  секретном файле на сервере; его нет ни в базе, ни в резервной копии.
- **Ротация**: при смене мастер-ключа перешифровываются только маленькие ключи файлов, а
  не сами файлы.
- **Проверка загрузки**: размер → тип по содержимому → разбор в изолированном потоке с
  лимитом времени и памяти → правила для PDF (пароль — отказ; JavaScript и
  launch-действия — отказ; **вложенные файлы — отказ в SignFlow**; существующая подпись —
  предупреждение). Belegscan из вложений читает только XML электронного счёта.
- ClamAV в v1 не ставим.

### Новые понятия

- **AES-256-GCM** — стандартный алгоритм шифрования, который заодно обнаруживает подмену
  зашифрованных данных.
- **DEK** (data encryption key) — ключ, которым зашифрован один файл.
- **KEK** (key encryption key), мастер-ключ — ключ, которым зашифрованы DEK.
- **Конвертное шифрование (envelope encryption)** — схема «ключ в конверте»: данные
  шифруются DEK, а DEK шифруется KEK.
- **Nonce** — одноразовое случайное число для каждого шифрования.
- **Магические байты** — первые байты файла, по которым виден его настоящий тип
  (`%PDF-`), что бы ни было написано в расширении.
- **Декомпрессионная бомба** — маленький файл, который при разборе раздувается до
  гигабайтов.
- **Worker thread** — отдельный поток Node.js; если он завис, его можно убить, не уронив
  сервер.

### Аналогия

Камера хранения. Каждая ячейка закрыта своим ключом (DEK). Все ключи от ячеек висят в
шкафчике, а шкафчик закрыт одним главным ключом (KEK), который администратор носит с
собой. Вор, укравший ячейки и шкафчик, ничего не откроет. Сменить главный замок — значит
перевесить один замок на шкафчике, а не переделывать все ячейки. Но администратор, у
которого главный ключ, откроет всё — и мы этого не скрываем.

### Что может сломаться

- **Потеря мастер-ключа = потеря всех файлов.** Нужна офлайн-копия (менеджер паролей и
  распечатка). Это записано в runbook.
- Взлом работающего сервера даёт доступ ко всему. От этого шифрование не защищает.
- Отказ PDF с JavaScript иногда отсечёт легитимный PDF-формуляр. Сообщение об ошибке
  должно объяснять причину.
- Удалённый файл остаётся в резервных копиях до 35 дней (ADR-0014). Пользователю это
  сказано прямо: «удалённое исчезает из резервных копий не позже чем через 35 дней».
- PDF с вложениями, в том числе электронные счета ZUGFeRD, через SignFlow в v1 отправить
  нельзя. Причина: мы пересылаем документ другим людям и не передаём скрытое содержимое.

### Вопросы с собеседования

1. **Что такое envelope encryption и зачем он?**
   Данные шифруются ключом файла, ключ файла — мастер-ключом. Ротация мастер-ключа не
   требует перешифровывать данные, а утечка одного ключа файла раскрывает один файл.
   EN: _"Each file has its own data key, wrapped by a master key — rotation re-wraps keys,
   not data."_

2. **От чего ваше шифрование защищает, а от чего нет?**
   Защищает от кражи диска, базы или резервной копии. Не защищает от администратора или
   взлома работающего сервера: там есть и ключ, и данные.
   EN: _"It protects data at rest — stolen disks, dumps and backups — not against a
   compromised running host. We state that explicitly."_

3. **Как вы проверяете загруженный файл?**
   Не доверяем расширению и заголовку: смотрим магические байты, разбираем файл в
   изолированном потоке с лимитами, отклоняем зашифрованные PDF и активное содержимое.
   EN: _"Validate by content, not by extension: magic bytes, a sandboxed parse with time
   and memory limits, and rejection of active content."_

## ADR-0013. Обработка PDF

### Что решили

- Подписи и печати в PDF ставит **сервер**. Браузер только показывает страницы и
  присылает картинку подписи и номер поля.
- PDF сохраняется **дописыванием в конец** (инкрементальное сохранение): байты оригинала
  не меняются никогда.
- После каждой подписи считается отпечаток SHA-256 новой версии и пишется в протокол.
- Страницу протокола в конце документа формирует сервер. Её язык выбирается в документе
  (по умолчанию — язык отправителя). **IP-адреса на странице по умолчанию скрыты
  частично** (`198.51.100.x`): итоговый PDF получают все участники, и мы не раздаём им
  адреса друг друга. Полный адрес хранится в базе и виден владельцу документа.
- Набор PDF для тестов — **только синтетические или открытые файлы**: репозиторий
  публичный, настоящих документов в нём быть не должно.
- Библиотека — `@cantoo/pdf-lib`, но **окончательно выбираем после пробной задачи** на
  наборе реальных PDF. Запасной вариант — LibPDF.

### Новые понятия

- **SHA-256, отпечаток** — число из 64 шестнадцатеричных знаков, вычисленное по файлу;
  изменился хоть один байт — отпечаток другой.
- **Инкрементальное сохранение** — способ изменить PDF, дописав изменения в конец файла.
- **Простая электронная подпись (SES)** — видимая отметка плюс журнал, без криптографии.
- **PDF.js** — библиотека Mozilla для показа PDF в браузере.
- **Встраивание шрифта (subset)** — в PDF кладутся только те буквы шрифта, что реально
  использованы.
- **Спайк** — короткая пробная задача, цель которой — ответ на вопрос, а не готовый код.

### Аналогия

Договор в папке с прошитыми страницами. Мы не переписываем страницы, а **подшиваем новые
листы сзади**: лист с подписью первого, лист с подписью второго, лист с протоколом. Первые
страницы остаются теми же физическими листами, и это можно проверить.

### Главное следствие

Первые N байт итогового файла — это и есть оригинал. Проверка «документ не изменён»
сводится к «посчитай отпечаток первых N байт и сравни». Длина N и отпечаток записаны в
протоколе. Заодно существующая цифровая подпись в загруженном PDF не разрушается.

### Что может сломаться

- Библиотека — форк, который поддерживают «пока он нужен авторам». Защита: интерфейс
  `PdfStamper`, набор тестовых PDF и названная замена.
- Повёрнутые страницы и нестандартные рамки: подпись может встать не туда. Отдельные
  тесты на пересчёт координат.
- Кыргызские буквы ң, ө, ү: шрифт для протокола должен их содержать. Проверяется в спайке.
- Программа просмотра может показать «документ изменён после подписания» для PDF с
  чужой цифровой подписью — поэтому при загрузке есть предупреждение.
- Картинка подписи сама по себе ничего не доказывает. Доказательство — протокол и
  отпечатки в нашей базе, пока в v2 не появится криптографическая печать сервиса.

### Вопросы с собеседования

1. **Почему PDF собирает сервер, а не браузер подписанта?**
   Браузер — недоверенная среда: изменённый клиент мог бы прислать PDF с другим текстом
   договора. Сервер принимает только входные данные и сам строит документ.
   EN: _"The client is untrusted; the server accepts inputs only and produces the document
   itself."_

2. **Как доказать, что документ не изменён?**
   Сохраняем дописыванием: оригинал остаётся префиксом итогового файла. Отпечаток SHA-256
   каждой версии записан в протокол.
   EN: _"Append-only incremental saves keep the original bytes as a prefix, and each
   version's SHA-256 is logged in the audit trail."_

3. **Как вы выбирали PDF-библиотеку при таком риске?**
   Спрятали её за интерфейсом, собрали набор реальных PDF с критериями прохождения и
   назвали альтернативу, которую проверим тем же набором.
   EN: _"Behind an interface, validated by a time-boxed spike against a real-world corpus
   with explicit pass criteria and a named fallback."_

## ADR-0014. Рабочее развёртывание

### Что решили

- **Новый отдельный сервер**: 2 vCPU, 4 ГБ RAM, 40 ГБ SSD.
- Всё запускается через **Docker Compose**: один файл описывает все контейнеры.
- **Caddy** принимает запросы из интернета и сам получает сертификаты HTTPS.
- **API и фронтенд — в одном образе** на продукт: они выкатываются и откатываются вместе.
- **Секреты** — в файлах на сервере, не в репозитории.
- **Миграции базы** выполняются отдельным шагом до запуска новой версии. Каждая миграция
  обязана работать и со старой версией приложения.
- **Выкат — вручную, кнопкой** в GitHub с вашим подтверждением. Выкатывается образ,
  собранный и проверенный в CI; пересборки нет. Откат — та же кнопка с предыдущей версией.
- **Резервные копии** — каждые 6 часов, зашифрованные, в хранилище в ЕС у другого
  провайдера; хранятся не дольше ~35 дней.
- **Раз в месяц автоматически проверяется восстановление**: копия разворачивается во
  временную базу, случайные файлы расшифровываются и сверяются по отпечатку.

### Новые понятия

- **Контейнер / образ** — упаковка программы со всем, что ей нужно; образ — «коробка»,
  контейнер — запущенная коробка.
- **Docker Compose** — файл и команда для запуска нескольких контейнеров вместе.
- **Обратный прокси** — программа на входе, которая принимает все запросы и раздаёт их
  нужным приложениям.
- **TLS** — шифрование соединения (замочек в адресной строке).
- **Миграция** — файл с изменением структуры базы (добавить таблицу, столбец).
- **Expand / contract** — сначала расширяем схему, не ломая старый код, потом выкатываем
  код, и только в следующем выпуске убираем старое.
- **Digest образа** — отпечаток образа; ссылка по нему всегда ведёт на те же байты.
- **RPO / RTO** — сколько данных допустимо потерять / за сколько надо восстановиться.
- **restic** — программа резервного копирования, которая шифрует копии до отправки.
- **Heartbeat-проверка** — сервис ждёт регулярного сигнала «я жив» и шлёт тревогу, если
  сигнал не пришёл.
- **Runbook** — пошаговая инструкция на случай аварии.

### Аналогия

Переезд магазина. Товар упакован в опечатанные коробки на складе (образы в CI) — в
магазин привозят именно эти коробки, а не собирают товар заново на месте. Перед открытием
переставляют полки (миграция) так, чтобы и старая выкладка ещё помещалась. Раз в месяц
проводят учения: «склад сгорел — восстановим ли мы магазин по страховым копиям?»

### Почему не на сервере с CRM

Общая зона поражения (взлом одного открывает другое), общие память и диск, общие
обновления и перезагрузки, один вход на порты 80/443. Допустимо только временно и при
условиях, перечисленных в ADR.

### Что может сломаться

- Один сервер: поломка железа — простой на часы, пока не восстановимся из копии.
- При выкате — несколько секунд недоступности.
- Миграция, несовместимая со старой версией, делает откат невозможным. Поэтому правило
  expand/contract и проверка миграций в CI.
- Потеряны мастер-ключ или пароль restic — копии не прочитать никому, включая нас.
- GitHub Actions получает SSH-доступ к серверу. Ограничиваем одной командой.

### Вопросы с собеседования

1. **Как устроен ваш выкат и откат?**
   Образ собирается один раз в CI, проходит e2e-тесты и публикуется с тегом коммита. В
   продакшен он идёт по кнопке с подтверждением; откат — тот же процесс с предыдущим
   коммитом, потому что миграции обратно совместимы.
   EN: _"Build once, promote the tested image by digest behind a manual approval; rollback
   is redeploying the previous digest because migrations are backward compatible."_

2. **Как вы меняете схему базы без простоя и с возможностью отката?**
   Expand/contract: добавляем новое, не удаляя старое; выкатываем код; старое убираем в
   следующем выпуске.
   EN: _"Expand-and-contract migrations: every migration works with the previous app
   version."_

3. **Откуда вы знаете, что резервные копии работают?**
   Ежемесячное автоматическое учение: восстановление во временную базу и сверка
   отпечатков случайных файлов; сбой или пропуск — тревога. Дважды в год — полное
   восстановление на чистом сервере по runbook.
   EN: _"A backup is only proven by a restore: an automated monthly restore drill with
   checksum verification, alerting on failure."_
