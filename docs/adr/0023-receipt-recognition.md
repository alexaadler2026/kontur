# 0023. Receipt recognition: ONNX models in a Web Worker behind an `OcrEngine` interface; the model is chosen by a spike with fixed criteria

- Status: Proposed, model pending spike
- Date: 2026-11-16

## Context and Problem Statement

Belegscan recognises receipts **in the browser with ONNX models** — decided by the design
and not reopened here (`business-processes.md`, process 1). Open is _which_ models, and
whether they read what real users have: production use is in Kyrgyzstan (Cyrillic, with
the Kyrgyz letters ң, ө, ү), the demo and full feature set are German (Latin). The owner
named this the main technical risk and asked for a spike as the first Belegscan task,
with the model decided by its result.

A second constraint from the owner: **the repository is public; real receipts never enter
it.** Real receipts are used for a local run only.

## Decision Drivers

- Decide on measurements from real receipts, not on model descriptions.
- Fields that carry money and dates matter more than perfect item names.
- Works offline; the photo does not leave the device for recognition.
- Download size and speed acceptable on a mid-range phone.
- The model must be replaceable without touching the parser or the UI.
- No personal data in the public repository.

## Considered Options

Candidates for the spike (not a final choice):

A. **PP-OCRv5 mobile models** (text detection + text recognition) converted to ONNX —
one recognition model for Latin script, one for East-Slavic Cyrillic
B. Tesseract.js with German, Russian and Kyrgyz data — **as a baseline only** (it is not
ONNX)
C. A recognition model with an extended character set (ң, ө, ү) — only if A fails on
those letters and it matters for the fields we need

## Decision Outcome

Decided now: **the frame, the procedure and the pass criteria.** The model is filled in
after the spike; this ADR's status is then updated.

### The frame

```
photo → crop and perspective → normalise → OcrEngine → text lines with boxes and confidence
      → receipt-parser → fields with confidence → editor
```

- **`OcrEngine`** is an interface: image in, lines out
  (`{ text, box, confidence }[]`). The ONNX implementation runs **in a Web Worker** on
  `onnxruntime-web` (WebAssembly; WebGPU when the browser offers it), so the UI never
  freezes.
- **`libs/receipt-parser`** turns lines into fields (merchant, date, items, tax lines,
  total, payment method) and is **independent of the engine**: pure TypeScript, tested
  with text fixtures, usable on the server too (`platform:neutral`, ADR-0007).
- **Field confidence** = recognition confidence of the source lines combined with the
  parser's own certainty (for example, a total confirmed by the item sum). The thresholds
  from `business-processes.md` apply to it: ≥ 85 % sure, 60–85 % check, < 60 % unsure.
- **Model files are served from our own origin**, not a public CDN: the app must work
  offline and should not tell a third party when a user scans. They are downloaded on the
  first scan with a progress indicator, cached by the service worker (ADR-0024) and
  addressed by content hash, so a new model version is a new file.
- The receipt's country (ADR-0026) selects the recognition model (Latin or Cyrillic).

### The spike

Compared on the same images: candidate A and baseline B (C only if needed).

**Data**

| Set       | Content                                                                                                                            | Where it lives                                                                               |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Real      | about 20 of the owner's receipts (Kyrgyzstan and Germany)                                                                          | **only on the owner's machine**, in a git-ignored directory; never committed, never uploaded |
| Synthetic | receipts generated by a script (German, Russian, Kyrgyz text; several layouts; blur, skew, low contrast) with known correct values | in the repository                                                                            |
| Open      | openly licensed samples, only if the licence allows redistribution                                                                 | in the repository, licence noted                                                             |

- A CI check fails if an image file appears outside the synthetic and open directories.
- Results from real receipts are recorded as **aggregate numbers only** — no images, no
  merchant names, no texts — in the journal.
- Regression tests in CI run on the synthetic set only.

**Measured per engine**

| Measure                                                           | Proposed pass mark                  |
| ----------------------------------------------------------------- | ----------------------------------- |
| Total amount read correctly                                       | ≥ 90 % of receipts                  |
| Date read correctly                                               | ≥ 90 %                              |
| Tax lines (rate and amount) correct                               | ≥ 80 %                              |
| Merchant name correct                                             | ≥ 70 %                              |
| Number of items matches                                           | ≥ 70 %                              |
| Fields marked "sure" that are in fact wrong                       | ≤ 5 %                               |
| Character errors on ң, ө, ү (reported, not a pass mark by itself) | —                                   |
| Time per receipt, reference Android phone / desktop               | ≤ 5 s / ≤ 2 s                       |
| Time per receipt, Safari on an iPhone (if one is available)       | measured and reported, no pass mark |
| Download size of all model files                                  | ≤ 25 MB                             |
| Peak memory in the tab                                            | ≤ 600 MB                            |

The pass marks were **confirmed by the owner on 2026-11-16**. Every measure is reported
**separately for Kyrgyz and German receipts**, and total amount and date are always two
separate numbers, never one combined figure.

**Reference phone** ("mid-range"): an Android phone of the middle class, two to three
years old, typical for Kyrgyzstan — Xiaomi Redmi Note 12 / 13 or Samsung Galaxy A34 / A35,
whichever is at hand — plus the owner's own phone. The journal names the exact model.

**Image size is a spike parameter.** Recognition runs on a reduced working copy
(ADR-0025). The spike measures the fields at two working sizes, because shrinking hurts
small print first; the smaller size is adopted only if it passes. The spike also records
the median text-line height below which fields start to fail — the threshold for the
"move closer" hint of ADR-0025.

**Why Kyrgyz letters may matter less than feared.** Amounts, dates and rates are digits;
the keywords around them (ИТОГО, НДС, НсП) are plain Cyrillic. ң, ө, ү appear mostly in
merchant and item names. The spike therefore measures **fields**, and reports character
errors separately.

**Outcomes**

- A passes → adopt A.
- A fails only on Kyrgyz-specific letters in names → adopt A; names are flagged "check"
  for Kyrgyz receipts; option C goes to the v2 list.
- A fails on amounts or dates for Kyrgyz receipts → production starts with manual entry
  for those fields (the editor already supports it) while option C is evaluated; the
  decision is taken with numbers in hand.

**Also verified in the spike:** the models' licence allows our use and redistribution;
multi-threaded WebAssembly needs cross-origin isolation headers — check that they do not
break PDF.js or other parts of the app; behaviour in Safari on iOS.

### Consequences

- Good: the riskiest assumption of Belegscan is tested before anything is built on it.
- Good: engine and parser are separable; a better model later is a file swap plus a rerun
  of the same measurements.
- Good: no real receipt can reach the public repository by accident.
- Bad: the model decision — and with it the quality users see — is not known today.
- Bad: synthetic receipts never fully match real ones; CI protects against regressions,
  not against reality. The local real-receipt run must be repeated before each model
  change.
- Bad: tens of megabytes on first use over mobile data.

## Pros and Cons of the Options

### PP-OCRv5 mobile (ONNX)

- Good: current model family with ONNX exports and browser SDKs; small "mobile" variants;
  separate Latin and East-Slavic recognition models.
- Bad: the East-Slavic model is described for Russian, Ukrainian, Belarusian and
  Bulgarian — Kyrgyz letters are not promised.

### Tesseract.js (baseline)

- Good: has Kyrgyz language data; long-established.
- Bad: not ONNX (outside the design decision); generally weaker on photographed, skewed
  receipts. Used to put candidate A's numbers in context.

### Extended character-set model

- Good: would close the Kyrgyz gap.
- Bad: needs training data and effort; only justified by spike results.
